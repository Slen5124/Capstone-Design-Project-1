# DB 설계 결정과 변경 근거

## 현재 기준

운영 public 스키마는 저장 테이블 20개와 필드 186개이며 조회·호환 뷰는 없다. 새 코드는 실제 테이블과 필드명에 맞춰 작성하고 BE가 필요한 조회를 조합한다. 이 문서는 요구사항, 결정 이유, 구현 결과와 남은 한계를 설명한다.

## 화면의 업무에서 시작한 설계

세계지도에서 매장을 고르고 간트 작업을 확인한 뒤, 카메라 AI 관측과 현장 증빙을 각각 받는다. 본사는 증빙·관측을 검토하고 변경 요청을 처리한다. 그 결과를 주간 보고서와 질문 답변의 근거로 사용한다. 이 흐름에서 독립적으로 관리할 자료와 반복되는 행위를 구분했다.

| 고려한 점 | 결정과 적용 | 이유 |
| --- | --- | --- |
| 여러 매장으로 확장 | sites와 공통 테이블을 사용하고 매장·공정표·작업 ID로 범위를 연결 | 매장 추가 시 같은 구조를 사용하며 사용자·사진·보고서가 서로 다른 매장에 섞이는 것을 방지 |
| 회사와 사용자의 소속 | organizations, users와 site_memberships를 분리 | 같은 사용자가 여러 매장에 참여할 수 있고 매장마다 회사·역할이 달라질 수 있음 |
| 간트 원본과 실제 변경 | 원본 start·finish와 effective_start·effective_finish를 구분 | 계획의 근거를 보존하고 일정 변경·지연을 추적해야 함 |
| 문서 작업 번호와 DB 식별자 | source_task_id와 UUID id를 구분 | 공정표 버전이나 매장마다 같은 작업 번호가 나타날 수 있음 |
| 제출·재제출·검토·대화 | task_events로 공통 이력을 관리하고 event_type·대상 ID로 구분 | 비슷한 시간순 이력과 담당자·본문·첨부 구조의 중복을 줄임 |
| 변경 요청 자체와 대화 | change_requests와 task_events.request_id를 연결 | 같은 작업에 여러 요청이 있어도 대화와 결정을 요청별로 추적 |
| 요청 승인과 실제 적용 | 결정·적용 이벤트를 나누고 트랜잭션·잠금·중복 제약 사용 | 승인한 요청이 아직 적용되지 않은 상태와 중복 적용을 구분 |
| AI 관측과 사람이 확인한 완료 | task_observations와 검토 이벤트를 분리 | 사진에서 보이는 설치 상태와 담당자가 확인한 작업 완료는 서로 다른 근거 |
| 가림과 실제 미설치 | 관측 상태·사유를 설치 비율과 함께 저장 | 인식할 수 없는 사진을 0%로 저장하면 진행 상태를 잘못 전달하게 됨 |
| 같은 작업의 반복 분석 | 대상·시야·근거 사진·revision을 연결 | 수정본을 구분하고 보고서가 어떤 분석 결과를 사용했는지 설명할 수 있음 |
| 실제 파일과 DB의 역할 | 파일은 저장소에 두고 files와 첨부 연결에서 참조 | 사진·문서의 중복과 DB 용량 부담을 줄이고 다운로드 권한·무결성을 관리 |
| 과거 보고서의 재현 | 생성본의 revision과 provenance를 남기고 보고서 입력을 보관 | 이후 사진·일정·검토가 바뀌어도 당시 보고서의 근거를 확인 |
| 현지 날짜와 비교 주차 | 매장 시간대와 보고 기간을 사용하고 당시 알려진 변경만 조회 | 다른 시간대의 사진과 미래 일정 변경이 지난주 설명에 잘못 포함되는 것을 방지 |
| 구조화할 정보와 가변 자료 | 연결·검색에 쓰는 핵심 필드는 컬럼과 FK로 두고 부가정보·실행 자료는 JSON 사용 | 검색·관계 검증과 다양한 자료 형식을 함께 지원. JSON 형식 검증이 추가로 필요함 |

## 테이블 통합의 기준

기본 현장·공정표·사진 저장 구조에서 업무 기능을 추가하면서 제출, 검토, 메시지, 결정, 알림과 실행 상태 등의 저장 구조가 늘었다. 다시 화면별 사용 방식을 검토하고 반복되는 이력·첨부 구조를 공통화했다.

- 매장·회사·사용자·공정표·작업·파일은 각각의 책임을 가진다.
- 관측값은 대상·시야·수정본을 기준으로 따로 관리한다.
- 요청은 발신·수신 회사, 변경 제안과 처리 상태를 가진다.
- 제출·검토·대화·결정·적용은 공통 이벤트와 첨부 연결을 사용한다.
- 원본 보고서와 AI 생성·승인본, 질문 보관은 생성·사용 목적에 맞춰 구분한다.

현재 요구사항에 맞춰 합의한 결과가 20개 테이블이다. 향후 기능과 데이터 사용량이 달라지면 조회 방식과 저장 구조를 다시 검토한다.

## 호환 뷰를 만들었다가 제거한 이유

통합을 처음 적용할 때는 운영 프로그램이 종전 테이블명과 컬럼명을 참조하고 있었다. 이때 기존 기능을 이어서 사용할 수 있도록 12개 조회·호환 뷰를 일시적으로 두었다.

이후 신규 구조에 맞춰 다시 개발한다는 방향을 확인했다. BE가 20개 테이블을 직접 읽고 쓰도록 변경하고 AWS의 뷰 12개와 전용 쓰기 함수를 제거했다. 프로젝트·주차 실행·분석·보고서 입력은 공통 이벤트의 시스템 실행 자료로 보존했다. JSON 안의 식별 태그는 데이터이며 SQL 테이블이나 뷰를 생성하지 않는다.

설계 기록에서 11개는 기본 구조, 20개는 최종 통합 구조를 뜻한다. 중간 구현의 테이블 수와 현재 합의 구조는 시점을 구분해 해석한다.

## 적용 때 확인한 사항

1. 운영 전체 백업을 만들고 복제 DB에서 전환 및 뷰 제거를 시험했다.
2. 모든 저장 테이블의 내용을 트랜잭션 안에서 비교해 자료가 변하지 않았는지 확인했다. JSON은 구조와 실제 값을 기준으로 비교했다.
3. 매장 간 첨부 연결, 검토 역할, 반려 사유와 요청의 단일 결정·적용을 검사했다.
4. 추가 기간 요청 코드의 등록·승인·적용·재시도와 이전 주·당시 다음 주 전망에 미래 변경이 섞이지 않는지 검사했다.
5. 뷰 없는 환경에서 프로젝트·주간 자료·기간 요청 조회와 보고서 초안 생성을 HTTP로 확인했다. 근거가 부족한 최종 보고서는 거부되는지도 확인했다.
6. 운영 적용 후 기존 자료와 보고서, 인증된 조회와 서비스 상태를 확인했다.
7. 깃 업로드 전 실제 접속 값·운영 데이터·백업을 제외하고 Gitleaks와 커밋 예정 diff 검사를 수행한다.

## 보안과 남은 연결

매장 범위의 FK와 일부 검토·결정 제약을 적용했다. 인증 사용자와 회사·역할을 확인하는 API, 최종 사용자별 RLS·컬럼 제한, 파일 접근 인가는 함께 연결해야 한다. 현재 내부 서비스 계정의 동작을 유지했으므로 테이블 통합이나 보안 패턴 검사 결과를 최종 사용자 권한 검증 완료로 설명하지 않는다.

AI 정규 관측·현장 증빙·보고서의 전체 화면 연결도 화면별로 추가 확인한다. 기존 실행 상태 저장과 정상 조회를 유지한 사실, 향후 구현할 기능을 구분해 기록한다.

## 프로젝트 설명에 사용할 문장

공사 관리 화면의 업무 흐름을 기준으로 다중 매장에 공통으로 사용할 DB를 설계했습니다. 매장·공정표·작업의 식별자를 분리하고, 반복되는 제출·검토·대화·결정은 공통 이벤트와 첨부 구조로 통합했습니다. 원본 일정과 적용 일정, AI 관측과 본사 완료 확인, 요청 승인과 실제 적용을 구분해 근거와 이력을 추적하도록 했습니다. 관측 수정본과 보고서 생성 근거를 저장하고 현지 날짜·주차를 기준으로 비교하도록 했습니다. 운영 적용은 백업과 복제 DB 검증을 거쳤으며, 신규 개발 방향에 맞춰 호환 뷰를 제거하고 20개 테이블을 직접 사용하는 구조로 정리했습니다. 사용자별 접근 제어와 화면 연결은 별도의 구현·검증 항목으로 관리하고 있습니다.

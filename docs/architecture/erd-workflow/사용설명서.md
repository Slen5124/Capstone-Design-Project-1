# ALOHA DB 신규 버전 사용설명서

20개 테이블 합의 설계 기준  |  2026년 11월 9일 적용 확인
기존 DB 접속 안내를 받은 개발 및 연동 담당자용

매장 공정표, AI 관측, 현장 증빙과 본사 검토를 연결하는 신규 버전의 사용 규칙을 정리했습니다. 업무 자료는 공통 테이블에 저장하고 매장·공정표·작업 ID로 구분합니다.

운영 public 스키마에 20개 저장 테이블과 186개 필드를 적용했습니다. 별도 12개 뷰는 호환·조회 경로입니다. 이 설명서는 적용된 구조의 사용 규칙을 설명하며, 사용자별 권한과 정규 업무 API의 연결 여부는 담당자와 확인합니다.

### 처음 사용할 때

1. 기존에 전달받은 PEM과 검증된 known_hosts로 SSH 터널을 열고, 본인에게 부여된 DB 계정으로 접속합니다. 접속 값과 비밀번호는 기존 비공개 안내를 사용합니다.

2. 사용할 매장, 공정표 버전과 담당 역할을 확인합니다. 공정표 작업과 사진의 촬영 위치를 연결하고, 각 작업의 확인 방법을 정합니다.

3. 카메라 AI 관측과 현장 담당자의 증빙을 각각 등록합니다. 본사는 대상 자료를 검토하고, 확정 결과를 주간 보고서의 근거로 사용합니다.

### 업무의 기준


| 항목 | 사용 규칙 |
| --- | --- |
| 작업의 식별 | task_id는 DB 작업 UUID입니다. 원본 간트의 작업 번호는 source_task_id로 따로 보관합니다. |
| 날짜와 주차 | sites.timezone과 공정표 버전을 기준으로 사진 날짜와 보고 기간을 정합니다. |
| 진행 상태 | 관측 가능한 범위에서 설치 ÷ (설치 + 미설치)로 계산하고 가림 등 인식 불가 영역은 제외합니다. |
| 완료와 지연 | 완료는 증빙과 본사 확인으로 확정합니다. 계획 종료일이 지났는데 완료되지 않은 작업은 지연으로 다룹니다. |

### 자료를 연결할 때

site_id → schedule_id → task_id 순서로 범위를 확인합니다. 제출·요청·관측은 각각의 ID로 관리하고, 같은 작업에 여러 건이 생겨도 대상 ID를 유지합니다.

## 20개 테이블의 역할

매장을 추가할 때는 아래 공통 테이블에 자료를 등록합니다. 실제 사진·문서 파일은 파일 저장소에 두고 DB에서 파일 ID와 업무를 연결합니다.


| 테이블 | 저장하는 내용 |
| --- | --- |
| sites | 매장 이름, 주소, 시간대와 지도 좌표 |
| organizations | 업무를 주고받는 회사 |
| users | 로그인 사용자와 표시 이름 |
| site_memberships | 매장별 사용자·회사 소속, 역할과 활성 상태 |
| locations | 촬영 위치와 카메라 연결 정보 |
| files | 파일 위치·종류·크기·상태와 매장 소유 범위 |
| schedules | 매장별 공정표 버전 |
| schedule_sources | 공정표 원본 파일과 표시 순서 |
| schedule_tasks | 작업 ID, 원본 일정, 분류와 적용 일정 |
| schedule_task_locations | 작업과 촬영 위치의 연결 |
| daily_records | 촬영 위치별 일일 대표 사진과 분석 파일 |
| gt_datasets | 학습용 정답 데이터셋의 버전과 파일 |
| model_versions | 분석 모델의 버전과 설정·가중치 파일 |
| task_observations | 작업에 연결한 AI 관측값과 수정본 |
| change_requests | 일정·작업 변경 요청과 발신·수신 회사 |
| task_events | 제출·재제출·검토·대화·결정·적용 이력 |
| task_event_files | 이력에 첨부한 사진과 문서의 연결 |
| weekly_reports | 등록된 원본 주간 보고서와 메타데이터 |
| agent_reports | AI 생성 보고서의 버전·승인과 근거 |
| question_archives | 보관할 질문·답변 문서의 제목과 파일 연결 |

task_events를 공통 이력으로 사용합니다. 제출, 검토, 요청 대화를 구분할 때 event_type과 해당 대상 ID를 함께 사용합니다.

### 현재 호환 경로

workflow_projects, workflow_cycles, workflow_vision_batches, workflow_manager_evidence, workflow_report_snapshots, workflow_vision_deliveries, workflow_extension_context는 저장 테이블이 아닌 호환 뷰입니다. 실제 자료는 task_events.details의 workflow_state에 보관합니다. 기존 프로그램의 문자열 ID와 보고서 JSON 형식은 유지합니다.

legacy_change_requests, legacy_site_memberships, site_organizations, change_request_decisions는 추가 기간 요청 코드의 호환 뷰이고 task_review_queue는 검토 목록입니다. 따라서 저장 테이블은 20개이며 뷰 12개는 별도로 셉니다. 일반 업무 이력을 조회할 때는 workflow_state를 제외하거나 필요한 event_type을 명시합니다.

processing_route의 값은 ai, field, manual_check입니다. 작업 분류 category_codes와 검토·완료 상태를 각각 관리합니다.

## 사진 제출과 본사 검토

### 카메라 사진과 AI 관측

locations에 촬영 위치와 카메라 공급자를 연결합니다. 수집기는 매장 현지 날짜 기준으로 대표 사진을 고르고 files와 daily_records에 연결합니다. 카메라 인증 원문은 비밀 저장소에서 관리하고 credential_ref로 참조합니다.

분석 결과는 task_observations에 등록합니다. site_id, schedule_id, task_id와 daily_record_id로 근거를 연결하고 target_key·view_key로 대상과 시야를 구분합니다. 같은 대상의 수정 결과는 revision을 높여 보관합니다.

관측값은 installed_ratio에 0~1로 저장하고 화면에서 100을 곱해 퍼센트로 표시합니다. 판단 상태는 status, 관측 불가 사유는 hold_reason에 기록합니다. 가림과 분석 실패를 설치율 0으로 바꾸지 않습니다. overlay_file_id로 분석 표시 사진을 연결합니다.

### 현장 담당자의 작업별 증빙

작업을 선택하고 사진과 설명을 제출합니다. 파일은 files, 제출 건은 task_events, 첨부 연결은 task_event_files에 저장합니다. 재제출은 새 이벤트로 등록해 이전 자료와 반려 사유를 보존합니다.

### 검토 대상과 결정을 연결하는 방법


| 검토 종류 | 연결 필드와 처리 |
| --- | --- |
| 현장 제출 검토 | task_events.target_event_id에 검토할 제출 이벤트를 연결합니다. |
| AI 관측 검토 | task_events.observation_id에 검토할 관측 수정본을 연결합니다. |
| 반려와 재촬영 | 결정 이벤트에 반려 사유를 남기고 현장 담당자가 새 사진을 제출하도록 합니다. |
| 완료 확인 | AI 관측 수락과 작업 완료 확인을 구분하고, 대상 증빙과 확인한 담당자·시각을 남깁니다. |

### 화면에서 확인할 내용

작업별 검토에서는 현장 증빙과 AI 관측의 출처, 제출 차수, 검토 상태와 사유를 함께 보여줍니다. 대표 사진을 고를 때는 검토 결과와 포함 여부를 반영해 사용할 최신 자료를 선택합니다.

## 변경 요청과 주간 보고서

### 일정과 작업 변경 요청

1. change_requests에 대상 작업, 발신·수신 회사, 변경 제안과 사유를 등록합니다. 같은 작업에 여러 요청이 있어도 요청별 ID를 유지합니다.

2. 요청 대화와 결정은 task_events.request_id로 연결합니다. 대화에 올린 파일은 task_event_files와 files를 통해 연결합니다.

3. 수신 측의 허용된 담당자가 대기 요청을 수락하거나 반려합니다. 반려 사유를 남기고, 요청 상태와 결정 이력은 같은 트랜잭션에서 기록합니다.

4. 승인된 일정 변경을 적용할 때 schedule_tasks.effective_start·effective_finish와 적용 이력을 함께 기록합니다. 원본 start·finish는 계획의 근거로 보존합니다. 승인과 실제 일정 적용을 구분합니다.

### 주간 보고서 생성

보고 기간과 겹치는 간트 작업을 조회하고, 작업별 관측·증빙·검토·변경 요청을 모읍니다. 지난주부터 이어진 작업은 이전 자료와 비교합니다. 이번 주에 처음 등장한 작업도 설명하되 지난주 설명은 생략합니다.

이번 주 미완료 작업은 다음 주 관리 항목으로 이어서 보여주고 지연·이월 사실을 표시합니다. 추가 기간 요청은 요청 여부, 결정과 실제 적용 상태를 구분해 정리합니다. 마지막에는 다음 주 계획을 제시합니다.


| 자료 | 저장 위치와 사용 |
| --- | --- |
| 등록한 원본 보고서 | weekly_reports의 report_file_id·metadata_file_id로 연결합니다. |
| AI 생성 보고서 | agent_reports에 기간, revision, status, 생성 파일과 provenance를 남깁니다. |
| 승인한 보고서 | approved_by·approved_at으로 승인자와 시각을 기록합니다. 재생성한 결과도 버전별로 보관합니다. |
| 질문과 답변 보관 | question_archives에 제목·질문 시각·archive_file_id를 저장하고 본문과 근거는 문서 파일에 남깁니다. |

에이전트는 허용된 조회 API로 근거를 받습니다. 생성 문장의 수치·날짜·근거를 검사한 뒤 본사가 내용을 검토합니다.

## 연동 담당자가 확인할 사항

### 접속 후 구조 확인

기존 안내로 DB에 접속한 뒤 아래 읽기 전용 조회를 실행합니다. 이 설명서의 테이블·필드와 조회 결과가 일치하는지 확인하고, 차이가 있으면 DB 담당자에게 적용 명세를 요청합니다.

```sql
SELECT current_database(), current_user;

SELECT table_name, column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN (
    'schedule_tasks', 'task_events', 'task_event_files',
    'task_observations', 'change_requests', 'agent_reports'
  )
ORDER BY table_name, ordinal_position;
```

### 연결 순서

인증·매장 권한·파일 접근을 먼저 연결합니다. 이어서 현장·간트 조회, 증빙·검토·변경 요청, 카메라·AI 관측, 보고서·질문 보관 순으로 연동합니다. 웹 화면은 권한을 확인하는 서버 API를 통해 자료를 주고받습니다.

### 권한과 파일 처리

매장별 행 접근은 site_memberships와 site_id를 기준으로 제한합니다. 요청 대화와 첨부에는 발신·수신 회사의 권한도 적용합니다. RLS는 행의 범위를, 컬럼 권한과 API 응답 규칙은 읽고 쓸 필드를 제한하도록 구성합니다.

인증 식별자, 카메라 인증 참조, 파일의 실제 경로와 내부 오류는 일반 화면 응답에서 제한합니다. 파일은 업로드·형식·상태 검증 후 업무에 연결하고, 다운로드할 때도 부모 작업이나 요청의 권한을 확인합니다. site_id가 없는 기존 파일은 관리자가 소유 매장을 확인한 뒤 새 업무에 연결합니다.

### 연동 완료 전에 확인

다른 매장의 자료와 요청 첨부에 접근할 수 없는지 확인합니다. 같은 요청을 동시에 결정해도 한 번만 반영되는지, 재시도 시 제출·첨부·적용 이력이 중복되거나 끊기지 않는지 확인합니다. 시간대, 가림, 사진 누락과 지난주 비교 범위도 함께 검사합니다.

005 통합은 운영에 적용했습니다. 같은 DB에 005나 새 설치 SQL을 다시 실행하지 않습니다. 새 빈 DB에는 020_twenty_tables_clean.sql을 사용하고 계정·권한을 별도로 구성합니다. 사용자별 RLS·컬럼 제한과 정규 업무 API 연결은 추가 구현·검증 단계입니다.
